Installation

cleanrules is pre-alpha and not on any package registry yet. Today you build it from the repository: the Python binding with maturin, the Rust crate as a path or git dependency, the C library with Cargo, C++ with CMake (or Conan or vcpkg, from the checkout), and the JavaScript package with npm. This page shows each of them, and the package names each language will use once it is published.

Requirements#

  • Rust 1.95 or later (the crate uses edition 2024), to build either the crate or the Python extension. Install it with rustup.
  • Python: CPython 3.11 or later for the binding. Free-threaded builds are supported (3.14t, and 3.15 and later with or without the GIL).
  • uv is the simplest way to build the binding; plain pip works too, because the package uses maturin as its build backend.
  • C++: a C++17 compiler and CMake 3.21 or later (Conan 2 or vcpkg optional).
  • JavaScript: Node 22.12 or later with npm to build; the package then runs on Node 22.12 or later, Deno 2.6 or later and browsers.

Python, from source#

Clone the repository and let uv build the extension into the binding's own virtual environment. uv run rebuilds it whenever the Rust sources change.

terminal
git clone https://github.com/cleanrules/cleanrules.git
cd cleanrules/bindings/python
uv run python -c "import cleanrules; print(cleanrules.__version__)"

To install it into another environment of yours, point an installer at the binding's directory. This builds a wheel with maturin and installs it:

terminal
uv pip install ./cleanrules/bindings/python      # or: pip install ./cleanrules/bindings/python

Then check what you have. Every cell in this manual ran in a session like this one:

PythonPython binding · runs
import sys

import cleanrules

print(cleanrules.__version__, cleanrules.FORMAT_VERSION)
print(sys.version)
Output
0.0.0 1
3.14.6 free-threading build (main, Jun 23 2026, 15:54:43) [Clang 22.1.3 ]

__version__ is the package version (0.0.0 until the first release) and FORMAT_VERSION is the version of the JSON format the core reads and writes. They are independent: the format has its own version, which only changes when a change to it is not additive.

Wheels and free threading#

The binding is built as three wheels per platform. CI is configured to build them for Linux (manylinux and musllinux, x86_64 and aarch64), macOS (arm64 and x86_64) and Windows (x64 and arm64). They will be published with the first release:

WheelFor
cp311-abi3CPython 3.11 to 3.14 with the GIL (the stable ABI)
cp314-cp314tfree-threaded CPython 3.14
cp315-abi3.abi3tCPython 3.15 and later, with or without the GIL (PEP 803)

The module supports free threading: importing it does not re-enable the GIL, and rule sets can be shared by threads. On builds with a GIL, evaluation releases it. See threads.

Rust, from source#

Depend on the crate by path (a local clone) or by git. The crate is named cleanrules and lives in crates/core of the repository's workspace.

Cargo.toml
[dependencies]
# a local clone of the repository
cleanrules = { path = "../cleanrules/crates/core" }
# or straight from the repository
# cleanrules = { git = "https://github.com/cleanrules/cleanrules" }

The core depends only on jiff (dates and time zones, with a bundled time-zone database), regex and thiserror, plus saphyr-parser behind the yaml feature, and has no unsafe code (unsafe_code = "forbid"). Every Rust program in this manual uses a path dependency like the one above. The quick start has a complete program.

C, from source#

The C ABI is the crate cleanrules-ffi in crates/ffi: one header, include/cleanrules.h, over a static and a shared library. Build it with Cargo and link your program to it:

terminal
cd cleanrules
cargo build --release -p cleanrules-ffi
cc -I crates/ffi/include program.c target/release/libcleanrules_ffi.a -lm -lpthread -ldl -o program
# on macOS, -lm alone; on Windows, the libraries cargo rustc --print native-static-libs lists

The header documents who owns every pointer, how errors are returned and what may be shared between threads. The C programs of the worked examples were built this way, and docs/examples/discounts.c in the repository shows native values, explanations and actions as C callbacks. The C++ CMake package below also installs the C header and library, with a cleanrules::c target.

C++, from source#

The C++ layer is one header, cleanrules.hpp (C++17, in bindings/cpp), over the C library. Its CMake project builds the library with cargo, so it needs a Rust toolchain and CMake 3.21 or later. Build, test and install it, then find it from your project:

terminal
cd cleanrules
cmake -S bindings/cpp -B build/cpp -DCMAKE_BUILD_TYPE=Release
ctest --test-dir build/cpp                      # builds, then runs the tests and every conformance vector
cmake --install build/cpp --prefix /opt/cleanrules
CMakeLists.txt
find_package(cleanrules CONFIG REQUIRED)        # with CMAKE_PREFIX_PATH=/opt/cleanrules
target_link_libraries(app PRIVATE cleanrules::cleanrules)   # C++; cleanrules::c for C

add_subdirectory(path/to/bindings/cpp) gives the same targets. The repository also has a Conan 2 recipe and a vcpkg overlay port; both build from the checkout, so the build machine needs cargo too:

terminal
conan create bindings/cpp/conan --build=missing                    # then [requires] cleanrules/<version>
vcpkg install cleanrules --overlay-ports=bindings/cpp/vcpkg/ports   # or list it in vcpkg.json with the overlay

The C++ programs of this site were built with CMake this way, against the installed package. ConanCenter and the vcpkg registry will get their ports with the first release. Options (a shared library, cross-compiling, the MSVC runtime, sanitizers) are in the C++ README; the API is in the C++ API chapter.

JavaScript and TypeScript, from source#

The package lives in bindings/js. It runs on Node 22.12 or later (a native addon built with napi-rs), Deno 2.6 or later and browsers (a WebAssembly build with the same API). Building it needs a Rust toolchain; the WebAssembly build also needs the wasm32-unknown-unknown target and the wasm-bindgen CLI at the version the crate pins:

terminal
cd cleanrules
npm --prefix bindings/js install            # the build tools: @napi-rs/cli and typescript
npm --prefix bindings/js run build:release  # the addon for this machine
rustup target add wasm32-unknown-unknown
cargo install --locked wasm-bindgen-cli --version 0.2.130
npm --prefix bindings/js run build:wasm     # the WebAssembly module, for browsers and Deno
npm --prefix bindings/js test               # the test suite and the conformance vectors, on the addon

Then depend on the directory from your project (npm install ../cleanrules/bindings/js, or a file: dependency) and import it:

app.ts
import { F, Rule, RuleSet } from 'cleanrules'   // Node and Deno pick their build
import { init } from 'cleanrules/wasm'           // browsers and bundlers: await init(url) first

On Node, where no addon fits the machine, node --conditions=browser runs the WebAssembly build. npm i cleanrules will work once the package is on npm: the main package, with the WebAssembly module, and one optional package per platform for the addon (Linux with glibc 2.28 or later or musl, macOS and Windows, x64 and arm64). The TypeScript programs of this site ran with Node 26 on the addon built this way. The API, the two builds and the JavaScript pitfalls are in the JavaScript API chapter.

Running the tests#

If you build from source, you can run the same checks the project runs:

terminal
cargo test --workspace                       # the core, the C ABI, their conformance vectors and property tests
(cd bindings/python && uv run pytest)        # the Python binding (builds the extension first)
cmake -S bindings/cpp -B build/cpp && ctest --test-dir build/cpp   # C++, with its conformance runner
npm --prefix bindings/js test                # JavaScript on the addon; test:wasm and test:deno for the others
