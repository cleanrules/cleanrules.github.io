Manual / Chapter 03

Quick start

A pricing rule set from start to finish: define three rules, evaluate one customer, read the decision, ask why a rule did not fire, and summarize the rule set. First in Python, then the same program in Rust.

Define the rules#

A Rule takes a name, a condition and a payload. F starts a field path into the input; comparisons and & (and), | (or), ~ (not) build the condition tree. The rule set uses the priority hit policy: among the rules that fire, the one with the highest priority wins.

PythonPython binding · runs
from decimal import Decimal

from cleanrules import F, Rule, RuleSet

rules = RuleSet(
    [
        Rule("vip", (F.customer.years > 5) & (F.order.total > 1000),
             {"discount": Decimal("0.15")}, priority=10),
        Rule("loyal", (F.customer.years > 2) | F.customer.newsletter,
             {"discount": Decimal("0.05")}, priority=5),
        Rule("blocked", F.customer.blocked, {"discount": 0}, priority=99),
    ],
    hit_policy="priority",
)
rules
Output
RuleSet([vip, loyal, blocked], hit_policy='priority')

Note blocked: its condition is a bare field, F.customer.blocked, so it fires when that field is True.

Evaluate an input#

Inputs are Python data: dicts and lists here, but also dataclasses, Pydantic models, namedtuples or pandas rows (reading Python objects). Only the fields the rules read are read, and the input is never modified.

PythonPython binding · runs
data = {"customer": {"years": 3, "newsletter": False}, "order": {"total": 800}}
decision = rules.evaluate(data)
decision
Output
<Decision priority: selected [loyal]>

output is the winner's payload, read-only. Payload values that were Decimals stay Decimals:

PythonPython binding · runs
decision.output
Output
mappingproxy({'discount': Decimal('0.05')})

Every rule has a result, in rule order. truth is a value of three-valued logic:

PythonPython binding · runs
for result in decision.results:
    print(f"{result.rule.name:<8} fired={result.fired!s:<5} truth={result.truth}")
Output
vip      fired=False truth=false
loyal    fired=True  truth=true
blocked  fired=False truth=unknown

blocked is unknown, not false: the input has no customer.blocked, and cleanrules does not guess. A rule only fires when its condition is true, so an unknown rule never fires. With strict=True the rule set would raise MissingFieldError instead (strict mode).

Ask why, and why not#

explain() explains every rule. why_not(name) picks one, typically one that did not fire:

PythonPython binding · runs
explanation = decision.explain()
explanation
Output
<Explanation: vip: not_fired, loyal: selected, blocked: unknown>
PythonPython binding · runs
why = decision.why_not("vip")
print(why.status, why.achievable)
for cause in why.causes:
    print(cause.node, "->", cause.truth, "| values:", cause.values)
    print("   needs", cause.counterfactual)
Output
not_fired True
F.customer.years > 5 -> false | values: ((('customer', 'years'), 3),)
   needs Counterfactual(path=('customer', 'years'), op='gt', target=5, gap=2)
F.order.total > 1000 -> false | values: ((('order', 'total'), 800),)
   needs Counterfactual(path=('order', 'total'), op='gt', target=1000, gap=200)

Each cause is one comparison of the rule's condition, with the value it read and a counterfactual: what the field would need (customer.years > 5) and how far it was (a gap of 2 years; the order was 200 short). achievable says that changing those values could make the rule fire. The unknown rule carries a structured reason:

PythonPython binding · runs
blocked = explanation.for_rule("blocked")
print(blocked.status, blocked.causes[0].reason)
Output
unknown Reason(code='missing_field', paths=(('customer', 'blocked'),), types=(), detail=None)

Summarize the rule set#

A summary describes a rule set without evaluating it: the fields it reads, where, and the outputs it produces.

PythonPython binding · runs
summary = rules.summary()
for usage in summary.fields:
    print(usage.path, "read by", usage.conditions)
Output
('customer', 'years') read by ('vip', 'loyal')
('order', 'total') read by ('vip',)
('customer', 'newsletter') read by ('loyal',)
('customer', 'blocked') read by ('blocked',)

The same, as JSON#

Decisions, explanations and summaries have a JSON form defined by the format specification; the core writes it, so it is the same in every language.

PythonPython binding · runs
import json

doc = decision.explain().to_dict()
print(doc["version"], doc["explanation"]["selected"])
vip_doc = doc["explanation"]["rules"][0]
print(json.dumps(vip_doc["requirement"]["all"][0]["counterfactual"]))
Output
1 ['loyal']
{"path": ["customer", "years"], "op": "gt", "target": 5, "gap": 2}

The same program in Rust#

Rust cannot overload > to build nodes, so comparisons are methods (gt, le, …) while &, | and ! are operators. An expression is a Build, which carries the first construction error and is checked once by .build(). Inputs here are written in the JSON format and read with read_value.

quickstart.rsRust core · runs
//! Quick start: build rules, evaluate, explain and summarize.
use cleanrules::build::{Build, constant, field};
use cleanrules::explain::{Requirement, explain, summary};
use cleanrules::format::{ValueContext, read_value, write_explanation, write_path, write_value};
use cleanrules::json::{Limits, parse, to_string};
use cleanrules::rules::{Config, HitPolicy, Rule, RuleSet};
use cleanrules::{Decimal, Value};

type Result<T> = std::result::Result<T, Box<dyn std::error::Error>>;

fn rule(name: &str, when: Build, discount: Build, priority: i64) -> Result<Rule> {
    let then = vec![("discount".to_owned(), discount.build()?)];
    Ok(Rule::with_payload(name, when.build()?, then)?.priority(priority))
}

fn main() -> Result<()> {
    let customer = || field("customer");
    let rules = RuleSet::new(
        vec![
            rule(
                "vip",
                customer().get("years").gt(5) & field("order").get("total").gt(1000),
                constant(Decimal::parse("0.15")?),
                10,
            )?,
            rule(
                "loyal",
                customer().get("years").gt(2) | customer().get("newsletter"),
                constant(Decimal::parse("0.05")?),
                5,
            )?,
            rule("blocked", customer().get("blocked"), constant(0), 99)?,
        ],
        Config {
            hit_policy: HitPolicy::Priority,
            ..Config::default()
        },
    )?;

    let text = r#"{"customer": {"years": 3, "newsletter": false}, "order": {"total": 800}}"#;
    let data: Value = read_value(&parse(text, &Limits::default())?, "", ValueContext::Data)?;
    let decision = rules.evaluate(&data)?;

    if let Some(output) = decision.output()? {
        println!("output: {}", to_string(&write_value(&output)));
    }
    let explanation = explain(&decision);
    for entry in &explanation.rules {
        println!("{:<8} {}", entry.rule, entry.status.as_str());
    }
    if let Requirement::Group(kind, items) = &explanation.rules[0].requirement {
        println!("vip needs {kind:?} of {} conditions", items.len());
    }
    for usage in summary(&rules).fields {
        println!(
            "{} read by {:?}",
            to_string(&write_path(&usage.path)),
            usage.conditions
        );
    }
    let json = to_string(&write_explanation(&explanation));
    println!("explanation JSON: {} bytes", json.len());
    Ok(())
}
Output
output: {"discount":{"$decimal":"0.05"}}
vip      not_fired
loyal    selected
blocked  unknown
vip needs All of 2 conditions
["customer","years"] read by ["vip", "loyal"]
["order","total"] read by ["vip"]
["customer","newsletter"] read by ["loyal"]
["customer","blocked"] read by ["blocked"]
explanation JSON: 1323 bytes

The decision is the same as in Python: the binding is a thin layer over this crate.
