Performance

The core is measured with criterion on a fixed workload, and the project does not claim a speed-up without a benchmark. This chapter gives the core's figures, explains what they include, and gives practical advice for the Python binding, whose own overhead has not been measured yet.

The Rust core#

The workload is a loan screening rule set of 12 rules that uses every family of node, and 1,000 deterministic applicants, some with missing or null fields. Each evaluation keeps every rule's full result tree, which is what explanations are built from. Measured on an Apple M5 with rustc 1.97.1, release profile; the interval is criterion's 95 % confidence interval of the mean.

In Python#

The binding is a thin layer: the core builds every node and evaluates every rule. The cost of crossing into Python (converting the input, creating the result objects) will be measured with each binding (/bench in the repository) before any figure is published. Meanwhile, these follow from how the binding works:

  • Build rule sets once and reuse them. Construction validates every node; evaluation does not repeat that work. Rule sets are immutable and thread-safe.
  • Evaluation releases the GIL on builds that have one, and free-threaded builds run evaluations in parallel threads (threads).
  • explain() and to_dict() evaluate the input again. A Python Decision keeps its rule set and the converted input, and rebuilds the core's decision when you ask for an explanation or a document. Evaluation is deterministic, so the result is the same, but explaining an input costs a second evaluation of it. output, outputs, results, selected and fired are read immediately and cost nothing extra.
  • Only the paths a rule set reads are read from the input, each object once, so passing a large object costs only what the rules use. Where a path ends, the value is converted whole: a payload such as {"doc": F.order} converts the whole order. rules.summary().fields lists the paths.
  • For many rows, evaluate_many evaluates a list in one call. Columnar evaluation over Arrow batches is planned (phase I).

Regular expressions#

Patterns compile once, when the node is built, and match in time linear in the input: no pattern can make evaluation hang, whatever the data. That is why look-around and backreferences are not available (regular expressions).
