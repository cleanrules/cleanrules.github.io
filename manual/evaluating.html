Manual / Chapter 07

Evaluating data

Real data has holes: missing keys, nulls, strings where numbers should be. cleanrules never guesses and never crashes on them. A condition it cannot decide is unknown, with a reason you can read; and when you prefer errors, strict mode raises them. This chapter also covers batches and threads.

Unknown, and why#

The same rule on five inputs. Only the first is decided; each of the others is unknown for a different, structured reason:

PythonPython binding · runs
from cleanrules import F, Rule, RuleSet

rules = RuleSet([Rule("adult", F.customer.age >= 18)])
for data in ({"customer": {"age": 42}}, {"customer": {}}, {"customer": None},
             {"customer": {"age": "42"}}, {"customer": {"age": True}}):
    d = rules.evaluate(data)
    cause = d.why_not("adult").causes[0] if not d.results[0].fired else None
    reason = cause.reason if cause else None
    why = f"{reason.code} at {reason.paths[0]} {reason.types}" if reason else ""
    print(f"{str(data):<29} {d.results[0].truth:<8} {why}")
Output
{'customer': {'age': 42}}     true     
{'customer': {}}              unknown  missing_field at ('customer', 'age') ()
{'customer': None}            unknown  null at ('customer',) ()
{'customer': {'age': '42'}}   unknown  type_mismatch at ('customer', 'age') ('string', 'number')
{'customer': {'age': True}}   unknown  type_mismatch at ('customer', 'age') ('boolean', 'number')
ReasonMeaning
missing_fieldthe path cannot be resolved; the reason's path goes up to where it failed
nulla null (None) or NaN was met; the path says where, even in the middle of a path
type_mismatchvalues of incompatible type groups (the reason lists both), or a non-boolean used as a condition
unorderablebooleans were ordered with <, <=, > or >=
division_by_zeroa division by zero
int_overflow, decimal_overflowan integer outside 64 bits, or a decimal in the data beyond 38 digits
nan_resultan arithmetic result is NaN, such as inf - inf
read_errorreading the data raised an error

A string "42" is not the number 42: cleanrules does not coerce types, so the comparison is a type mismatch rather than a guess. Reasons appear in explanations as cause.reason (explanations of unknown rules).

Three-valued logic#

Under Kleene's logic, & is false as soon as one operand is false, | is true as soon as one is true, and ~ of unknown is unknown. A rule fires only when its condition is true. This is how SQL treats NULL.

a & b

TUF
TTUF
UUUF
FFFF

a | b

TUF
TTTT
UTUU
FTUF

~a

a~a
TF
UU
FT
PythonPython binding · runs
from cleanrules import Const

checks = RuleSet([
    Rule("and_false", (F.missing > 1) & Const(False)),
    Rule("or_true", (F.missing > 1) | Const(True)),
    Rule("not_unknown", ~(F.missing > 1)),
], hit_policy="rule_order")
d = checks.evaluate({})
print([(r.rule.name, r.truth.value) for r in d.results])
Output
[('and_false', 'false'), ('or_true', 'true'), ('not_unknown', 'unknown')]

One consequence: ~(F.x > 5) is not the same as F.x <= 5 when x is missing; both are unknown, and neither fires. To make missing data count, say so explicitly with is_null():

PythonPython binding · runs
review = RuleSet([Rule("manual_review", F.score.is_null() | (F.score < 500))])
print(review.evaluate({}).fired, review.evaluate({"score": None}).fired, review.evaluate({"score": 640}).fired)
Output
('manual_review',) ('manual_review',) ()

Arithmetic never raises#

A division by zero, an overflow or a NaN result gives null with its reason, and the comparison over it is unknown. Strict mode does not change that: it only raises for missing fields, type mismatches and read errors.

PythonPython binding · runs
ratio = RuleSet([Rule("high_debt", F.debt / F.income > 0.6)])
d = ratio.evaluate({"debt": 1200, "income": 0})
print(d.results[0].truth, d.why_not("high_debt").causes[0].reason)
Output
unknown Reason(code='division_by_zero', paths=(('debt',), ('income',)), types=(), detail=None)

Exact comparisons#

Ints, floats and decimals compare by exact value. The decimal 0.10 equals the decimal 0.1, but the float 0.1 is not exactly one tenth, so it does not:

PythonPython binding · runs
from decimal import Decimal

money = RuleSet([Rule("ten_percent", F.rate == Decimal("0.1"))])
print(money.evaluate({"rate": Decimal("0.10")}).fired, money.evaluate({"rate": 0.1}).fired)
Output
('ten_percent',) ()

Keep money in Decimals, in the data and in the rules.

Strict mode#

With strict=True, a missing field or a type mismatch raises instead of becoming unknown. The error is a MissingFieldError or a TypeMismatchError, both EvaluationErrors, and names the rule, the full path and the types:

PythonPython binding · runs
from cleanrules import MissingFieldError, TypeMismatchError

strict = RuleSet([Rule("adult", F.customer.age >= 18)], strict=True)
for data in ({"customer": {"name": "Ana"}}, {"customer": {"age": "42"}}, {"customer": None}):
    try:
        print(strict.evaluate(data).fired)
    except (MissingFieldError, TypeMismatchError) as err:
        print(f"{type(err).__name__}: rule={err.rule} path={err.path} types={err.types}")
Output
MissingFieldError: rule=adult path=('customer', 'age') types=()
TypeMismatchError: rule=adult path=('customer', 'age') types=('string', 'number')
()

A null in the middle of a path is not an error, even in strict mode: the path exists up to a null, so the last input above simply does not fire. Strict mode raises the first error in rule order, and within a condition the first in left-to-right order, so the same input always produces the same error.

Strict mode and is_null#

is_null() is true for a null, but in strict mode a missing key is still an error, because strict mode is for data whose shape you control. Send an explicit None for "no value":

PythonPython binding · runs
lenient_null = RuleSet([Rule("no_email", F.email.is_null())], strict=True)
print(lenient_null.evaluate({"email": None}).fired)
try:
    lenient_null.evaluate({})
except MissingFieldError as err:
    print(err)
Output
('no_email',)
rule 'no_email': missing field email, in `F.email`

The order validation example shows both modes side by side on a messy record.

Batches#

evaluate_many(rows) evaluates each input in order and returns a list of decisions. In strict mode, the error of the first failing input carries its position as row:

PythonPython binding · runs
rows = [{"customer": {"age": 30}}, {"customer": {"age": 12}}, {"customer": {}}]
print([d.fired for d in rules.evaluate_many(rows)])
try:
    strict.evaluate_many(rows)
except MissingFieldError as err:
    print(err.row, "|", err)
Output
[('adult',), (), ()]
2 | rule 'adult': missing field customer.age, in `F.customer.age` (input 2)

A string, a mapping or a data frame is not a collection of inputs, and is rejected at once rather than iterated by mistake:

PythonPython binding · runs
from cleanrules import EvaluationError

try:
    rules.evaluate_many({"customer": {"age": 30}})
except EvaluationError as err:
    print(err)
Output
evaluate_many takes an iterable of inputs, got dict
hint: for a single input use evaluate(data); for several pass a list of them

For pandas, pass df.to_dict("records"); for polars, df.iter_rows(named=True). Vectorized evaluation over Arrow batches, with the same nulls, types and reasons, is planned (phase I).

Threads and free threading#

Rule sets and decisions are immutable, so one rule set can be shared by any number of threads. On Python builds with a GIL, evaluation releases it while the core works. On free-threaded builds there is no GIL at all, and the module does not re-enable it. The cell below ran on such a build:

PythonPython binding · runs
import sys
from concurrent.futures import ThreadPoolExecutor

batch = [{"customer": {"age": age}} for age in range(10, 30)]
with ThreadPoolExecutor(max_workers=8) as pool:
    fired = list(pool.map(lambda row: rules.evaluate(row).fired, batch))
print(sum(1 for f in fired if f), "adults of", len(fired))
print("GIL enabled:", getattr(sys, "_is_gil_enabled", lambda: True)())
Output
12 adults of 20
GIL enabled: False

Reading Python objects#

The input does not have to be a dict. When a rule set is built, the binding works out the tree of paths its conditions and payloads read, and reads only those paths, each object once. A path segment reads:

  • a key of a mapping (checked with in first, so __missing__ is never triggered);
  • a key of a record: a namedtuple, or an object with keys() such as a pandas row;
  • an index of a sequence (never of a string or a mapping);
  • a public data attribute of any other object, properties included: dataclasses, attrs classes and Pydantic models (by field name, not alias). Never a name starting with _, a method, a class, a module, or an attribute of a scalar.
PythonPython binding · runs
from dataclasses import dataclass
from typing import NamedTuple

from pydantic import BaseModel


@dataclass
class Customer:
    name: str
    age: int


class Order(NamedTuple):
    total: float
    country: str


class Applicant(BaseModel):
    customer: Customer
    order: Order


spain = RuleSet([Rule("adult_es", (F.customer.age >= 18) & (F.order.country == "ES"))])
print(spain.evaluate({"customer": Customer("Ana", 42), "order": Order(120.0, "ES")}).fired)
print(spain.evaluate(Applicant(customer=Customer("Bo", 17), order=Order(80.0, "ES"))).fired)
Output
('adult_es',)
()

pandas rows work whichever way you iterate, and a missing value in a column (NaN, NaT, pandas.NA) is null, so the third row is unknown rather than "not low":

PythonPython binding · runs
import pandas as pd

low = RuleSet([Rule("low_score", F.score < 500)])
df = pd.DataFrame({"name": ["Ana", "Bo", "Cy"], "score": [420, 610, None]})
print([d.fired for d in low.evaluate_many(df.to_dict("records"))])
print([low.evaluate(row).results[0].truth.value for _, row in df.iterrows()])
print([low.evaluate(row).fired for row in df.itertuples()])
Output
[('low_score',), (), ()]
['true', 'false', 'unknown']
[('low_score',), (), ()]

numpy scalars, datetime64 and arrays are converted too (arrays as lists). A getter that raises gives a null with the reason read_error; in strict mode, the EvaluationError keeps the original exception as its __cause__. An AttributeError means the attribute is missing.

PythonPython binding · runs
class Flaky:
    @property
    def age(self):
        raise RuntimeError("database is down")


d = rules.evaluate({"customer": Flaky()})
print(d.results[0].truth, d.why_not("adult").causes[0].reason.code)
try:
    strict.evaluate({"customer": Flaky()})
except EvaluationError as err:
    print(type(err).__name__, err.code, "| cause:", repr(err.__cause__))
Output
unknown read_error
EvaluationError evaluation_error | cause: RuntimeError('database is down')

Where a path ends, the value is converted whole, with a depth limit and cycle detection: an object becomes a map of its public data attributes. A value with no equivalent in the data model (bytes, a set, a function…) is opaque: rules cannot look inside it, and it comes back as the very same object.

PythonPython binding · runs
class Invoice:
    def __init__(self, number):
        self.number = number
        self._internal = "never read"


pdf = b"%PDF-1.7 ..."
echo = RuleSet([Rule("echo", Const(True), {"invoice": F.invoice, "attachment": F.attachment})])
out = echo.evaluate({"invoice": Invoice("F-2026-118"), "attachment": pdf}).output
print(out["invoice"])
print(out["attachment"] is pdf)
Output
{'number': 'F-2026-118'}
True
