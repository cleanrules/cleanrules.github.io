Hit policies and aggregates

Several rules may fire on the same input. The hit policy decides what that means: one winner, every match, a sum, or an error that tells you two rules disagree. The six policies follow DMN, the decision-table standard, with a few deliberate deviations listed at the end.

One rule set, six policies#

Three discount tiers, and a customer of seven years with an order of 1,500, so all three rules fire. The cells below evaluate the same rules under each policy.

PythonPython binding · runs
from cleanrules import F, Rule, RuleSet

tiers = [
    Rule("standard", F.order.total > 100, {"discount_pct": 5}, priority=1),
    Rule("loyal", F.customer.years > 2, {"discount_pct": 10}, priority=5),
    Rule("vip", (F.customer.years > 5) & (F.order.total > 1000), {"discount_pct": 15}, priority=10),
]
data = {"customer": {"years": 7}, "order": {"total": 1500}}

Single-hit policies#

first, priority, unique and any select at most one rule, and decision.output is its payload, or None when nothing fired.

PythonPython binding · runs
for policy in ("first", "priority", "any", "unique"):
    try:
        d = RuleSet(tiers, hit_policy=policy).evaluate(data)
        print(f"{policy:<9} selected {[r.rule.name for r in d.selected]} -> {dict(d.output)}")
    except Exception as err:
        print(f"{policy:<9} {type(err).__name__}: {err.message} {err.rules}")
Output
first     selected ['standard'] -> {'discount_pct': 5}
priority  selected ['vip'] -> {'discount_pct': 15}
any       HitPolicyError: rules fired with different outputs under the any hit policy ('standard', 'loyal', 'vip')
unique    HitPolicyError: 3 rules fired under the unique hit policy ('standard', 'loyal', 'vip')
PolicySelectsRaises HitPolicyError whenUse it for
firstthe first rule that fired, in rule orderneverordered checks: the most specific rule first, a fallback last
prioritythe rule that fired with the highest priority; ties go to rule orderneveroverrides: a "decline" beats an "approve" whatever the order
uniquethe only rule that firedmore than one fireddecision tables whose rows must not overlap
anythe first rule that firedthe rules that fired have different payloadsrules that must agree, such as several ways to qualify for the same plan

unique and any turn overlapping or inconsistent rules into an error that lists every rule involved, instead of a silent choice. unique raises as soon as a second rule fires, before computing any payload. The worked examples show both: a shipping table under unique and discount channels under any.

Multi-hit policies and aggregates#

rule_order and collect select every rule that fired, in rule order. Read their payloads from decision.outputs. With an aggregate, collect combines them into one output, key by key:

PythonPython binding · runs
d = RuleSet(tiers, hit_policy="rule_order").evaluate(data)
print([dict(o) for o in d.outputs])
for aggregate in ("sum", "min", "max", "count"):
    d = RuleSet(tiers, hit_policy="collect", aggregate=aggregate).evaluate(data)
    print(f"collect + {aggregate:<5} -> {dict(d.output)}")
Output
[{'discount_pct': 5}, {'discount_pct': 10}, {'discount_pct': 15}]
collect + sum   -> {'discount_pct': 30}
collect + min   -> {'discount_pct': 5}
collect + max   -> {'discount_pct': 15}
collect + count -> {'discount_pct': 3}
  • sum, min, max need numbers. Decimals are converted to floats first, as arithmetic does. min and max return the value unchanged, so the minimum of 2 and 3.5 is the int 2.
  • count counts the non-null values of each key.
  • Nulls are skipped, as in SQL; a key whose values are all null sums to null.
  • Without an aggregate, collect is the same as rule_order, and decision.output raises HitPolicyError because there are several outputs (see the fraud flags example).

When nothing fires, single-hit decisions have no output, and so does a collect aggregate:

PythonPython binding · runs
d = RuleSet(tiers, hit_policy="first").evaluate({"customer": {"years": 1}, "order": {"total": 50}})
print(d.selected, d.output)
d = RuleSet(tiers, hit_policy="collect", aggregate="sum").evaluate({"customer": {"years": 1}, "order": {"total": 50}})
print(d.output, d.aggregated)
Output
() None
None None

An aggregate that meets a value that is not a number raises, naming the rules whose payloads hold one; count works on any value:

PythonPython binding · runs
from cleanrules import HitPolicyError

labels = [Rule("a", F.x > 0, {"label": "small"}), Rule("b", F.x > 5, {"label": "large"})]
try:
    RuleSet(labels, hit_policy="collect", aggregate="sum").evaluate({"x": 9})
except HitPolicyError as err:
    print(err.rules, "|", err.message)
print(dict(RuleSet(labels, hit_policy="collect", aggregate="count").evaluate({"x": 9}).output))
Output
('a',) | cannot sum the non-numeric output "label"
{'label': 2}

Why a rule that fired was not selected#

The explanation of a rule that fired but lost carries a Note: who won, and why.

PythonPython binding · runs
d = RuleSet(tiers, hit_policy="priority").evaluate(data)
for entry in d.explain().rules:
    print(entry.rule, entry.status, entry.note)
Output
standard fired Note(kind='lower_priority', winner='vip', priority=1, winner_priority=10)
loyal fired Note(kind='lower_priority', winner='vip', priority=5, winner_priority=10)
vip selected None
NoteWhen
lower_prioritypriority, and the winner's priority is higher
same_prioritypriority, and the winner has the same priority but comes first
any_agreesany: the outputs agree, and the policy reports the first
earlier_ruleany other policy: the winner comes first

Choosing a policy#

  • A list of checks with a fallback at the end: first.
  • Rules written by different people, where some must override others: priority. See the loan approval and agent guardrail examples.
  • A table where exactly one row should match: unique, so an overlap is an error rather than a silent first match.
  • Independent rules that must give the same answer: any.
  • Every problem found, such as validation errors or fraud flags: rule_order.
  • Adding up contributions, such as premium surcharges or risk points: collect with sum (see the insurance premium example).

Deviations from DMN#

  • Aggregates apply per payload key; DMN aggregates a single output column.
  • count counts non-null values; DMN engines differ on whether it counts matches or distinct outputs.
  • priority uses each rule's priority, not DMN's ordered list of output values. Decision tables (task D.3) will compile output-value priorities into rule priorities.
  • collect without an aggregate keeps rule order, so results are deterministic; DMN leaves the order unspecified.
