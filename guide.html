Concepts guide

How cleanrules decides and explains.

One engine, one set of semantics, written down in a specification and enforced by 2,135 conformance vectors. This guide walks through it from the condition tree to the explanation, with a real example for every idea.

Every JSON output on this page is real output of the Rust core, produced by running the examples through crates/core and written with its own JSON writer. The text renderings of explain() and summary() are real output of the core too, printed through the Python binding. Python code uses the Python binding, which runs today; for a hands-on tour with real Python output, read the manual.

1 · Conditions as data

A condition is a tree you can read, not a function you call.

In most rule libraries a condition is a lambda: the engine can run it, but cannot look inside. In cleanrules a condition is an immutable syntax tree of nodes with stable lowercase tags (and, gt, field…). Users build it idiomatically in each language, such as (F.customer.years > 5) & (F.order.total > 1000) in Python, and the tree is the same everywhere.

Because the engine can see the tree, it can:

  • explain which leaf made a rule fire or fail, and by how much;
  • serialise it to a versioned JSON document that every language reads the same way;
  • audit it statically, vectorise it over Arrow batches and compile it into a Rete network (all planned);
  • cross language boundaries without callbacks: a rule written in Java is evaluated by the same core in Go.

Trees are checked when they are built. Each node has a kind: a condition yields a truth value, a value yields a value, and any (fields and boolean constants) depends on the data. Comparing two conditions, using a number as a rule's condition or putting a null constant anywhere except under is_null is an ExpressionError at construction, never a surprise at evaluation time.

2 · Node catalogue

Every node, the same in every language.

Each node is a JSON object with an "op" key and one key per field. A missing key, an unknown key or an unknown op is a format error; breaking a construction rule is an expression error (format).

3 · Three-valued logic

True, false and unknown: Kleene logic, as in SQL.

Crisp logic in cleanrules has three truth values. A missing field or a null makes a comparison unknown, and unknown propagates through the connectives with Kleene's tables, which are the same rules SQL uses for NULL. A rule fires only when its condition is true.

The tables are checked by 21 hand-picked conformance vectors (ast/truth/*), and the core's tests check them exhaustively over all 27 combinations, together with De Morgan, double negation, associativity and distributivity. Property tests check De Morgan and double negation again on randomly generated condition trees.

The evaluator never combines truth values with a language's && or ||: every connective goes through a Logic trait. Today that trait has one implementation, Kleene logic, registered as "boolean". Fuzzy t-norms and s-norms from fuzzytool will plug into the same place (phase J).

Proposed, pending confirmation (phase J): under a fuzzy logic, unknown becomes the interval [0, 1] and each connective is applied to the endpoints, which reduces exactly to Kleene's tables on {0, 1}.

4 · Unknown values

Missing data is never a crash, and never a silent false.

When a truth value is unknown or a value is null, the result records a reason: a stable code, the field paths involved and the type groups. A true or false result never carries one. Implementations are compared on the code, paths and groups; the human-readable detail may change.

Reason codes (spec/ast.md, Results and reasons)
CodeMeaning
missing_fieldthe path cannot be resolved
nulla null value (or NaN) was met; the path says where
type_mismatchvalues of incompatible groups, a list, map or opaque value, or a non-boolean used as a condition
unorderablebooleans were ordered with <, <=, > or >=
division_by_zeroa division by zero
int_overflowan integer outside the signed 64-bit range
decimal_overflowa decimal in the data that does not fit in 38 digits
nan_resultan arithmetic result is NaN
read_errorreading the data raised an error

Type groups

Values compare only within a group: number (ints, floats and decimals), string (ordered by Unicode code point), boolean, date, naive_datetime, aware_datetime (compared by instant) and other (lists, maps, opaque values). Numbers compare exactly: 2⁵³ + 1 is not the float 2⁵³, and the decimal 0.1 is not the float 0.1.

A null in the middle of a path

customer.age with customer null is null with reason null and the path where the null was met. NaN read from data is null in every language, because languages disagree on how NaN compares.

5 · Strict mode

When unknown should be an error, ask for strict.

A rule set with "strict": true raises instead of returning unknown, for exactly three causes: a missing field (MissingFieldError, even under is_null), a type mismatch (TypeMismatchError, including ordering booleans) and a read error (EvaluationError chained to the original). Nulls, division by zero, overflows and NaN results stay nulls with their reasons, and a null in the middle of a path is accepted.

The error raised is the first one in depth-first, left-to-right post-order: children before their parent, operands in order, rules in rule order. Every engine mode raises the same error; in a batch, the first failing input, with its row.

Payloads are evaluated only for the selected rules (and every fired rule under any), so a rule that fired but lost never raises because of its payload.

Errors carry stable codes and context that conformance vectors compare: the rule, the full field path, the type groups, the row. Messages are written by the core, so they read the same in every language.

6 · Rules and payloads

A rule is a condition, a payload and a name.

KeyRequiredMeaning
nameyesunique and non-empty within the rule set
whenyesthe condition: a node of kind condition or any
thennothe payload: keys mapped to value nodes, in order
prioritynoa signed 64-bit int, default 0, used by priority
tagsnoa set of strings
descriptionnofree text, shown in explanations
metadatanokeys mapped to data values

Payload values are expressions, not just constants: "rate": base_rate × 2 is computed from the input when the rule is selected. A field in a payload passes through whatever the data holds, lists and maps included. Payload member order is significant: it is the order of the output's keys and the order in which values are evaluated.

Actions (do) are code of the host language. evaluate is pure and never runs them, so a decision can be computed any number of times for explanations, validation or model predictions. run evaluates, then calls the actions of the selected rules in rule order (task D.4 adds actions by registered name).

7 · Hit policies

Six DMN hit policies decide which rules win.

Every rule's condition is evaluated, in rule order. Among the rules that fired, the rule set's hit policy selects the winners. Errors are HitPolicyError and list the rules involved.

PolicySelectsErrorUse it when
firstthe first fired rule—rule order expresses precedence, often with a catch-all rule last
prioritythe fired rule with the highest priority; ties go to rule order—precedence should not depend on where a rule is written
uniquethe fired rulemore than one firedrules are meant to be mutually exclusive, and an overlap is a bug to report
anythe first fired rulefired rules have different payloadsrules may overlap as long as they agree
rule_orderevery fired rule, in rule order—you need every match, as a list (outputs)

Outputs

outputs are the payloads of the selected rules, in rule order. output is the winner's payload for single-hit policies (null when nothing was selected) and the aggregate for collect with one; for rule_order and collect without an aggregate, asking for it is an error, as the table shows. Outputs are read-only.

Aggregates

Applied per payload key over the selected payloads. Nulls are skipped, as in SQL, and count counts non-null values. Decimals are converted to float64 before sum, min and max; an integer sum outside 64 bits and a NaN sum are null; with nothing selected the aggregate is null.

Deliberate deviations from DMN

  • Aggregates are per payload key; DMN aggregates one output column.
  • count counts non-null values; DMN engines differ on what C# counts.
  • priority uses each rule's priority; decision tables (task D.3) will compile DMN's output-value priorities into rule priorities.
  • collect without an aggregate keeps rule order, because results must be deterministic.

8 · Explanations

Why each rule fired, and what would change it.

An explanation is built only from a decision's result trees and its rule set: nothing is evaluated again. A decision read back from JSON explains exactly like the original. Each rule gets a status and a requirement: the elementary conditions behind its outcome.

Rule status
StatusMeaningText
selectedthe hit policy selected it[x]
firedit fired, but the policy chose another rule; a note says why[x]
not_firedits condition is false[ ]
unknownits condition is unknown[?]
Notes for rules that fired but were not selected
NoteWhen
lower_prioritypriority, and the winner's priority is higher
same_prioritypriority, same priority, the winner comes first
any_agreesany: the outputs agree, the first is reported
earlier_ruleany other policy: the winner comes first

Requirements: all and any

A requirement is a cause (one elementary condition: a comparison, in, is_null, a string test, a field used as a condition, a between half) or a group of at least two requirements: all (each one matters) or any (one is enough).

For an and that is false, the group is all of the operands that are not true: fixing only the false ones would leave the result unknown. For an or that fired, it is any of the true operands. A not flips the role of the connective below it (De Morgan), so not (a or b) is explained as needing a and b to be false.

The requirement is then simplified: nested groups of the same kind are spliced, repeated causes merged, and absorption applied (a and (a or b) needs only a).

Finally, for rules that did not fire, every way to make them fire is checked against the whole tree, because a condition can occur in several places, possibly under a not. Only options that really make the rule fire are kept; if none does, the rule is marked "achievable": false: its conditions conflict.

9 · Counterfactuals

“Short by 2”, exactly, in the value's own type.

A cause that does not hold, is not unknown, and compares one field with one constant gets a counterfactual: the field's path, the comparison it needs, the target and, when it can be computed, the gap.

  • A constant on the left is flipped (5 < x becomes x > 5), and a negated cause is negated (> becomes <=).
  • The gap is target − value for gt/ge and value − target for lt/le; 0 for a strict comparison exactly at its limit.
  • eq and ne have no distance; a counterfactual without a gap is given when the cause is negated.

Gap arithmetic is exact whenever it can be:

ValuesGap
two intstheir difference, checked in 64 bits
a float and an int or floatthe float64 difference
two decimals, or a decimal and an intthe exact decimal difference, larger scale kept: 10.05 − 9.9 = 0.15
a decimal and a floatno gap
two dates{"days": n}
two naive or two aware datetimes{"microseconds": n} (aware: between UTC instants)

10 · Summaries

What a rule set reads and writes, without running it.

summary() describes a rule set statically: its configuration (policy, aggregate, logic, strictness); its rules with their priorities, output keys and whether they have an action; the fields it reads, in order of first appearance, each with the rules whose condition reads it and the (rule, key) pairs whose payload reads it; every output key; and the tags with their rules.

The field list is also what a binding reads from native data: it converts only the paths the rule set reads, never the whole object. The planned MCP server will derive each rule set's input schema from it (agents).
