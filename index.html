Rules you can read, run and explain.

cleanrules is a rules engine with one Rust core and the same semantics in Rust, C/C++, Python, JavaScript, Java/Scala, Go and Erlang. Business rules, expert systems, data validation, ML explanations and guardrails for AI agents — and every decision tells you why.

Status at a glance

The Rust core, Python, C, C++ and JavaScript are done; Java runs from source.

Phases A (the contract between languages), B (the Rust core), C (the Python binding), D (rules as data: JSON, YAML, a text syntax, decision tables and actions by name) and E (the C ABI and a header-only C++17 wrapper, with a CMake package, a Conan recipe and a vcpkg port) and F (JavaScript and TypeScript: a native addon for Node, prebuilt per platform with a glibc 2.28 floor, and a WebAssembly build for browsers and Deno, sharing one idiomatic API and passing the conformance suite) are complete. Phase G, the JVM, is in progress: the Java binding (Java 25 and later, through the FFM API over the C ABI, with no native code of its own) has its native layer and its idiomatic API (conditions and rules in code, decisions, structured explanations and summaries, documents, ruleFromText, decision tables and result trees) on the main branch; the native libraries inside the jar are in review, the Scala 3 layer is being written, and the Java conformance runner and Maven Central come last. That is 58 of the 96 tasks of the roadmap. Everything builds from source today, and nothing is published to any registry yet (crates.io, PyPI, npm, Maven Central, Conan, vcpkg): the Python binding will be the first public release, and the 1.0 release will ship every language together. One engine, four jobs

Write a rule once. Use it everywhere it matters.

Business rules

Priorities and DMN hit policies — FIRST, PRIORITY, UNIQUE, ANY, RULE_ORDER, COLLECT with aggregates — exact decimals and immutable outputs.

in the Rust core

Expert systems

Forward chaining on a Rete network in Rust, deterministic agenda, truth maintenance and a derivation tree for every conclusion.

planned · phase K

Data validation

The same rules, vectorised over Apache Arrow batches, with the same nulls, types and reasons as row-by-row evaluation — and an explanation per row.

planned · phase I

ML explanations

Extract rules from models (trees, RuleFit, fuzzy rules via fuzzytool), measure fidelity and coverage, then run and audit them in any language.

planned · phase L

AI agents

Deterministic decisions for agents that are not.

The engine never calls a language model: agents call the engine. Through an MCP server or an adapter for their framework they get decisions that are reproducible, explained and auditable — and the explanation tells the model what would change the outcome.

A tool for agents

An MCP server, cleanrules-mcp, offers evaluate, explain, summary and validate over your rule sets, read-only, to Claude, the OpenAI Agents SDK, LangGraph or any MCP client.

Guardrails on tool calls

Before an agent acts, a rule set decides allow, deny or ask, and tells the model why. The decision is an audit record that can be read back and verified.

Rules from LLMs, verified

Rules are data, never code. A rule a model proposes is validated, audited, tested against cases and approved by a person before it is used. No eval, ever.

Adapters for frameworks

Thin, optional adapters for the Claude Agent SDK, OpenAI Agents SDK, LangChain, Pydantic AI, the Vercel AI SDK, LangChain4j and Spring AI. Everything else connects through MCP.

Why cleanrules

Conditions are data, not opaque code.

Every condition is a serialisable syntax tree. That single decision is what lets the engine explain, audit, vectorise and cross language boundaries without changing meaning.

Explanations with counterfactuals

Not just “rule fired”: which requirements held, which failed, which were unknown — grouped as all of / any of — and what would change the outcome (“short by 2”).

Three-valued logic

Missing fields, nulls, type mismatches and overflow become unknown with a structured reason, evaluated with Kleene logic. Strict mode turns them into errors when you want that.

One core, eight languages

All semantics live in the Rust core. Bindings only build rules idiomatically, convert data and run your actions — so a rule written in Java decides exactly the same in Go.

Fuzzy logic built in phase J

Swap the logic, keep the rules: t-norms, s-norms and complements from fuzzytool, with firing degrees and α-thresholds. Same &, |, ~ operators.

Static audit phase J

Find unsatisfiable conditions, shadowed rules, overlaps, contradictions and coverage gaps before they reach production.

Deterministic and safe

Same inputs, same decision, same firing order, same explanation — on every platform. No eval, linear-time regex, no unsafe in the core.

main.rs (excerpt)Rust core · runs
let years = || field("customer").get("years");
let discount = |d: f64| -> cleanrules::Result<_> {
    Ok(vec![("discount".to_owned(), constant(d).build()?)])
};
let vip = Rule::with_payload(
    "vip",
    (years().gt(5) & field("order").get("total").gt(1000)).build()?,
    discount(0.15)?,
)?;
let loyal = Rule::with_payload("loyal", years().gt(2).build()?, discount(0.05)?)?;
let rules = RuleSet::new(vec![vip, loyal], Config::default())?;

let decision = rules.evaluate(&data)?;
if let Some(output) = decision.output()? {
    println!("{}", to_string(&write_value(&output)));
}
for entry in explain(&decision).rules {
    println!("{}: {}", entry.rule, entry.status.as_str());
}

Pricing.javaJava binding · runs
import static io.github.cleanrules.Conditions.*;

import io.github.cleanrules.*;
import java.util.Map;

public class Pricing {
    public static void main(String[] args) {
        RuleSet rules = RuleSet.of(
                Rule.named("vip")
                        .when(field("customer", "years").gt(5).and(field("order", "total").gt(1000)))
                        .then("discount", 0.15),
                Rule.named("loyal").when(field("customer", "years").gt(2)).then("discount", 0.05));

        Decision decision = rules.evaluate(Map.of("customer", Map.of("years", 3), "order", Map.of("total", 1500)));
        System.out.println(decision.output().orElseThrow());

        RuleExplanation why = decision.whyNot("vip");
        Cause cause = why.causes().getFirst();
        System.out.println(why.status().jsonName() + " because " + cause.node() + " is " + cause.truth().jsonName()
                + " - short by " + cause.counterfactual().orElseThrow().gap().orElseThrow());
    }
}
Output

Roadmap

Specification first, then the core, then every language.

The semantics are a written specification and its conformance vectors, which the Rust core and every binding pass.

  1. A

    Contract between languages

    JSON format and schemas, neutral data model, and the conformance vectors every language runs.

  2. B

    Rust core

    Everything above in Rust, passing 100% of the vectors. Property tests and benchmarks.

  3. C

    Python binding

    Wheels (abi3, free-threaded cp314t and abi3t), the API (F, rules, decisions, explanations, errors), reading of dataclasses, Pydantic models and pandas rows, actions, and a conformance runner that passes every vector. It will be the first public release.

  4. D

    Rules as data

    JSON and YAML, a text syntax aligned with fuzzytool, decision tables from JSON, CSV, rows and data frames, and actions by registered name.

  5. E

    C and C++

    The C ABI: a header generated by cbindgen, native values, actions as C callbacks, decision tables row by row, checked under Miri and sanitizers. cleanrules.hpp: a header-only C++17 layer with handles that free themselves, exceptions or error_info values, a CMake package, a Conan recipe and a vcpkg overlay port. Both pass every conformance vector, C++ also under AddressSanitizer and UndefinedBehaviorSanitizer.

  6. F

    JavaScript and TypeScript

    A napi-rs addon for Node (prebuilt per platform in CI) and a WebAssembly build for browsers and Deno, with one idiomatic TypeScript API: F and .and(), .or(), .not(), rules, decisions with native values, structured explanations and summaries, documents, ruleFromText and decision tables. A conformance runner on both builds and Deno, and the npm packages checked and installed on every platform in CI. Not on npm yet.

  7. G

    Java and Scala

    Java 25 and later through the Foreign Function & Memory API over the C ABI, with no native code of its own. On the main branch: the native layer and the idiomatic API (field("customer", "age").ge(18), Rule.named(...), RuleSet.builder(), decisions, structured explanations and summaries, documents, ruleFromText, decision tables and result trees). Next: the native libraries inside the jar (in review), an idiomatic Scala 3 layer with &, | and ~ (being written), and the conformance runner and Maven Central. In progress.

  8. H, N

    Go, Erlang

    Each binding with its own conformance runner; Go over the C ABI, Erlang through a rustler NIF.

  9. I–L

    Validation, fuzzy & audit, expert system, ML

    Arrow batches, fuzzy norms, static audit, Rete, rule extraction from models.

  10. O

    AI agents

    An MCP server, guardrails for agent tool calls, adapters for agent frameworks, and verified rules proposed by LLMs.

  11. V

    Visualisation

    Conditions, rules, tables, decisions and explanations as diagrams, the same in every language.

  12. 1.0

    Synchronised release

    crates.io, PyPI, npm, Maven Central, Go modules, Hex, Conan and vcpkg. Paper and DOI.

Family

A sibling of fuzzytool.

cleanrules shares its author and its style with fuzzytool, a fuzzy-logic toolkit for Python: the same operators (&, |, ~), name-resolved registries and the verbs explain(), audit(), summary() and rule_from_text(). fuzzytool's norms are the reference for the fuzzy logic in the Rust core.
