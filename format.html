JSON format · version 1

The contract between languages.

A rule written in Java and read in Go is the same tree and decides the same way. That holds because every binding reads and writes one versioned JSON format, defined in spec/json-format.md, with JSON Schemas for editors and 187 conformance vectors for readers.

The Rust core reads condition, rule, rule set and decision documents and writes all six kinds today. Every example output and error on this page was produced by the core from the input shown. Loading rule files in JSON and YAML from every binding is task D.1.

Documents and versioning

One envelope, six kinds of content, strict readers.

A document is UTF-8 JSON (RFC 8259) without a byte order mark. Its top level is an object with "version": 1 and exactly one content key: condition, rule, ruleset, decision, explanation or summary. An optional "$schema" string is ignored by readers, so editors can find the schema. Writers put version first.

Readers are strict, because leniency would let readers in different languages build different trees:

  • an unknown key, anywhere, is a format_error: ignoring it could silently change what a rule means;
  • a duplicate key is a format_error: JSON parsers disagree on which duplicate wins;
  • invalid UTF-8, a byte order mark and an escaped lone surrogate are rejected, and strings are never Unicode-normalized.

Versioning

Adding a node, a content key or an optional key keeps the version; so does accepting a new JSON form that existing documents never use. Renaming, removing or changing the meaning of anything increases it. Optional keys added later are omitted at their default, so documents that do not use a new feature stay readable by older readers. A document from a newer format gets unsupported_version before anything else is checked. The format version is independent of the package versions.

vip.condition.json
{
  "version": 1,
  "condition": {
    "op": "and",
    "operands": [
      {
        "op": "gt",
        "left": {"op": "field", "path": ["customer", "years"]},
        "right": {"op": "const", "value": 5}
      },
      {
        "op": "gt",
        "left": {"op": "field", "path": ["order", "total"]},
        "right": {"op": "const", "value": 1000}
      }
    ]
  }
}

Documents are compared as parsed trees, never as text: members in order, numbers by lexical class and exact value (1 and 1.0 differ, 100.0 equals 1e2), and the sign of a float zero.

Values

Bare JSON where it is unambiguous, typed values elsewhere.

JSON has no integer, decimal or date types of its own. A value is either bare JSON or a typed value: an object with a single key starting with $. Writers always use the canonical form; the other forms exist for writers that cannot produce it.

Out-of-range values

An int outside 64 bits or a decimal beyond 38 digits is a format_error in a constant, but reads as null with reason int_overflow or decimal_overflow in data, so one bad value never rejects a whole input. A float literal that rounds to infinity (1e400) is an error; one too small (1e-400) reads as 0.0.

Time zones

Zone names are case-sensitive and kept as written, aliases included. The offset must be the zone's offset at that instant, which also picks the right time when a clock change repeats an hour. The time zone database is bundled with the core, not taken from the operating system, so a document is valid or invalid in the same way on every machine.

Any other $-key is a format_error, so new types can be added without changing what existing documents mean.

Conditions

Shape first, then the construction rules.

A condition node is an object with "op" (the node's tag) and one key per field; the full table is in the guide. A reader first checks the shape: missing, unknown or wrongly typed keys and unknown ops are format_error. It then builds the tree with exactly the construction rules the API applies, so a document can never hold a tree that the API could not build. Breaking one is an expression_error:

  • path rules: non-empty, no empty string segment, no negative index;
  • node kinds: a condition is not a value operand, a value is not an operand of and, or or not;
  • a null constant only under is_null or as a whole payload value;
  • arithmetic only on number constants;
  • and and or need two operands as written, before flattening;
  • in values non-empty, non-null and from one type group;
  • between constant bounds from one orderable group;
  • a matches pattern valid in Rust's regex syntax.

The error points to the node whose construction fails: for a wrong operand, the node that takes it.

Canonical writing

Keys in table order with op first; closed always written; and/or flattened; in values ascending (numbers by exact value, with equal numbers of different types all kept, decimal before float before int; strings by code point; false before true; dates and datetimes in time order); values in canonical form.

Payload order is part of the meaning.

Member order matters. The order of then is the order of a decision's output keys and the order in which strict mode reports payload errors. Many tools reorder JSON objects (Go's map[string]any, PostgreSQL's jsonb, jq -S, JavaScript's integer-like keys), so every binding reads and writes through an order-preserving representation.

Policy, aggregate and logic names are lowercase and matched exactly. This version defines one logic, "boolean" (Kleene). An unknown logic name is a registry_error; one the format defines but this build lacks will be unsupported, naming the Cargo feature.

A rule's own checks come after its nodes are built, in this order: a non-empty name, a when that is not a value, no condition as a payload value. A rule set's come after all its rules: unique names, aggregate only with collect, a known logic.

Writers omit optional keys at their default, but always write hit_policy and logic: together they say how the rule set decides. Actions are host-language code and are not part of version 1; a writer rejects them with unsupported unless asked to omit_actions.

Reserved: an object form of logic with parameters and an alpha threshold for graded logics (phase J). Version 1 readers reject both with format_error; adding them will not change the version.

Decisions

A decision is an audit record that can be read back and verified.

A decision document records every rule's result tree, so it can be explained or audited later without evaluating again. Rules are named, not copied: a decision is always read together with the rule set that produced it. Outputs are not stored, because they follow from the payload trees.

Reading a decision: eight checks

After its shape, the reader checks that the decision belongs to the rule set, in this order; the first failure is a decision_mismatch with a pointer:

  1. hit_policy, aggregate and logic are the rule set's;
  2. results name exactly its rules, in order;
  3. each tree matches the rule's nodes: ops, paths, children, constants;
  4. then is present exactly where payloads are evaluated;
  5. each node's truth, value and reason is what evaluation gives from its children;
  6. fired agrees with when;
  7. selected is what the hit policy selects;
  8. aggregated is what the aggregate gives.

So a decision a reader accepts is exactly one the core could have produced for some input. Leaves hold what was read from the input and are taken as they are.

A decision holds the values its conditions and payloads read, which may include whole lists or maps and personal data, so audit logs that store decisions must be treated like the input.

Reserved for later versions: ruleset_digest, a digest of the rule set document that readers will verify once a canonical byte form exists to hash, and metadata such as a correlation id. The core never stamps times or ids itself, so decisions stay deterministic.

Explanations and summaries

Output-only documents for user interfaces and logs.

An explanation document is the JSON form of explain(). It is output only: readers reject it with unsupported, because it follows deterministically from a decision and its rule set, which are the documents to store. To reproduce a past explanation, store the decision, the rule set and the core version.

Its top level holds hit_policy, logic, selected and one entry per rule: rule, status, a note for fired, achievable for not_fired and unknown, and the requirement.

A requirement is a cause or {"all": [...]} / {"any": [...]}. A cause holds condition, at (a JSON Pointer into the decision document), truth, negated, values, and reason and counterfactual when they apply. A counterfactual's gap is a number, {"days": n} or {"microseconds": n}.

A summary document holds the configuration and the arrays rules, fields, outputs and tags, always written even when empty. Examples of both are in the guide.

Limits and error order

A hostile file cannot exhaust memory or the stack.

LimitDefaultCounted
document size16 MiBbytes of JSON text
JSON nesting1024arrays and objects, the top-level object is 1, checked while parsing
node depth256condition or payload nodes, the root is 1, before flattening

Callers can raise the limits but never disable them. Exceeding one is limit_exceeded. The core's JSON reader is iterative, with an explicit stack; it was tested with 200,000 levels of nesting.

A reader reports one error, the first it finds in this order:

  1. size, JSON nesting and syntax, duplicate keys included, in text order (located by 1-based line and column, in Unicode code points);
  2. version, before any other key;
  3. shape and node depth, depth first in pre-order: an object's known keys in table order, then its unknown keys in text order (located by a JSON Pointer into the document as written);
  4. construction rules, in post-order: children before parents; in a rule, the condition, then payload values, then the rule's own rules; in a rule set, the rules, then its own rules.

Every implementation must report the same first error at the same location; the 187 reading vectors check it.

JSON Schemas

Schemas for editors, the specification for everything else.

The JSON Schemas (draft 2020-12) cover values and every kind of document, each with valid and invalid examples checked in CI. Point an editor at them with "$schema" to get completion and early warnings.

A schema cannot express everything: exact literals, numeric ranges, duplicate keys, construction rules and limits are defined by the specification, and the error code is always the specification's. When a schema and json-format.md disagree, the specification wins.
