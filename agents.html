Planned · phase O of the roadmap

Deterministic decisions for agents that are not.

Agents built on language models are flexible and unpredictable. Some decisions should be neither: whether a payment needs approval, whether a command may run, whether a customer qualifies. cleanrules plans to give agents those decisions as a tool, a guardrail and a verified target for the rules they propose, with an explanation that tells the model what would change the outcome.

Everything on this page is planned (phase O, after the rules-as-data phase D). Snippets marked design preview show intent, not an API. The one thing that already works is the engine underneath: the guardrail rule set and its decisions in the example below are real output of the Rust core today.

Principle

The AI uses the engine. It is never part of it.

Neither the core nor any binding will ever call a language model. Agents reach cleanrules from the outside, through an MCP server and thin adapters for their frameworks. This is a design decision of the project (D13), and it keeps three properties that agents themselves cannot offer:

  • Determinism. The same rule set and input give the same decision, the same firing order and the same explanation, in every language and on every run.
  • Explanations a model can act on. Not only “denied”, but which conditions held, which failed, and counterfactuals such as “needs context.hour >= 20”.
  • Audit. Each decision is a JSON document that can be stored, read back with its rule set and verified to be one the engine could have produced.

It also keeps the core's dependencies minimal: no model SDKs, no network.

A tool for agents

Evaluate, explain and summarise rule sets from any MCP client, read-only.

A guardrail on tool calls

A rule set decides allow, deny or ask before the agent acts, and says why.

A verified target for LLM-written rules

Rules are data. A proposed rule is validated, audited, tested and approved by a person before use.

MCP server · planned (tasks O.1–O.2)

cleanrules-mcp: rule sets as tools.

A binary in crates/mcp that serves the rule sets of a configured directory to any MCP client: Claude, the OpenAI Agents SDK, LangGraph and others. The Rust MCP SDK is still to be confirmed (the official rmcp is proposed).

Planned tools (task O.1)
ToolPurpose
list_rulesetsthe rule sets the server offers
evaluatea decision for one input
explainthe decision's explanation, in a compact form sized for a model's context
summarywhat a rule set reads and outputs, without evaluating it
validatecheck a rule or rule set document, with errors a model can correct

Input and output JSON Schemas derive from format v1, and each rule set's input schema is generated from its summary(): the fields it reads and their types. The rule sets are also offered as MCP resources.

  • Transports: stdio and streamable HTTP.
  • Read-only by default. The server never runs actions; it evaluates and explains.
  • Bounded. Limits on document size and on time, on top of the format's own limits.
  • Errors a model can correct: every error carries a stable code, a JSON Pointer to the offending value, a message and a hint, as the core already produces (see the format page).
  • Tested against the core: each tool's output must match the core's.

Guardrails · planned (task O.3)

Allow, deny or ask, before the agent acts.

A rule set receives a tool call (its name, arguments and context) or a model output, and decides. The verdict and its explanation go back to the model; the decision document goes to the audit log.

Planned integrations

  • Claude Agent SDK: its hooks, such as PreToolUse.
  • OpenAI Agents SDK: its guardrails.
  • LangGraph: its nodes and interrupts.

Why a decision document

The decision records every rule's result tree and the values read. Reading it back with its rule set runs eight checks, from the policy to every truth value, so a stored record that was altered, or that comes from a different rule set, is rejected with a pointer to the first mismatch. The core does this today (see the format page).

Works today

The guardrail itself is just a rule set.

The integration is planned; the decision logic is not waiting for it. The rule set below is a valid format v1 document, and the three scenarios are real decisions and explanations produced by the Rust core now. Note how the explanation for the payment tells the model that deny_outside_hours would need context.hour < 8 or >= 20.

Rules written by agents · planned (task O.5)

A model may propose a rule. It never runs one unchecked.

Because conditions are data, a rule proposed by a model is a JSON document, never code: there is no eval anywhere in cleanrules. Before it decides anything, it goes through a loop, offered as MCP tools and as an API.

  1. Propose

    The model writes a rule or rule set as a format v1 document, from a policy in natural language.

  2. Validate

    Shape and construction rules, with errors that carry a pointer, a message and a hint the model can correct.

  3. Audit

    Static audit (task J.4): unsatisfiable conditions, shadowed rules, overlaps, contradictions and gaps.

  4. Test

    Run the rules against cases with known expected decisions.

  5. Approve

    A person approves the rule before it is used.

  6. Deploy

    Only then is the rule set loaded where agents and services use it.

The roadmap also plans an evaluation set (natural-language policies to rules) with metrics of validity and of accuracy on held-out cases. Later, after the expert system (phase K), agents can feed facts from their tools into forward chaining, with the derivation tree as the explanation (task O.6).

Adapters · planned (task O.4)

Thin and optional, one per framework.

Each adapter turns a rule set into a tool of its framework. Adapters are optional extras loaded lazily, tested against pinned versions of each framework, and contain no decision logic. MCP stays the stable base for everything else.

Security model · planned (task O.7)

Assume the data and the rules may be hostile.

ThreatMitigationStatus
Prompt injection through the data being evaluatedData is never an instruction to the engine. The MCP server is read-only and never runs actions.engine: today · server: planned
Untrusted rule setsRules are data, never code; no eval. Regular expressions run in linear time (no lookaround, no backreferences). Readers enforce size, nesting and depth limits. A rule can only read map keys and public data attributes, never private members, methods or modules.core: today · bindings: specified
Incorrect or malicious rules proposed by a modelValidation, static audit, tests against cases and human approval before deployment.planned
Resource abuseFormat limits (16 MiB, 1024 nesting, 256 node depth) plus size and time limits in the server.format: today · server: planned
Altered or misattributed audit recordsDecisions are read back with their rule set and verified node by node (decision_mismatch).today
Personal data in audit logsDecisions hold the values they read, so stored decisions must be protected like the input itself.documented

The threat model and one guide per framework are part of task O.7. Planned integrations may change as agent frameworks evolve; MCP is the stable base.
