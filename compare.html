Where cleanrules fits.

cleanrules covers ground that several mature tools already cover, each in its own niche and language. This page says where it aims to differ, what exists today, and what is still a plan.

A fair warning first. The tools named here are established projects used in production. cleanrules is pre-alpha: its Rust core is complete in the repository, and no package is published yet. The table states goals, with their status, not a feature-by-feature verdict. The only measured comparison so far is with zen-engine, on one workload.

What is different by design

Not one feature: the combination.

Conditions as a serialisable tree

Not lambdas. The engine can explain, write, read back, audit and vectorise every condition, and a condition crosses language boundaries unchanged. Guide

A swappable logic

Every connective goes through one trait. Kleene's three-valued logic today; fuzzy t-norms and s-norms later, with the same rules. Guide

Explanation and audit as outputs

Every decision explains itself with requirements, values read and exact counterfactual gaps, and is a document that can be verified later. Guide

One core, eight languages

All semantics in one Rust crate; bindings only build rules, convert data and run actions, so they cannot diverge. Overview

One conformance suite

2,508 vectors with exact expected outputs, run today by the core and by the Python, C, C++ and JavaScript bindings, and by every binding before it ships, through JSON and through native data.

A stable bridge to agents

Planned: an MCP server and thin adapters, with the engine never calling a model itself. Agents

FAQ

Common questions.

Can I use cleanrules today?

From Rust, Python, C, C++ and JavaScript or TypeScript, by building from the repository (installation). The Rust core implements the whole specification and passes all 2,508 conformance vectors. The Python binding's API is done (conditions, rules, decisions, explanations, summaries, errors, actions, rule files, decision tables) and it reads dicts, dataclasses, Pydantic models and pandas rows; it passes every conformance vector (all 2,508 through JSON, 1,952 with native Python data) and will be the first public release. The C ABI (cleanrules.h, a static and a shared library) passes every vector too, and so does the header-only C++17 layer (cleanrules.hpp, with a CMake package, a Conan recipe and a vcpkg port built from the repository). The JavaScript package, a native addon for Node and a WebAssembly build for browsers and Deno, passes every vector on both builds; its npm packaging is being prepared. Nothing is on a registry yet, and the API may change before the first release. The other languages follow (see the roadmap). The intended package names are cleanrules on crates.io, PyPI, npm and Hex, and io.github.cleanrules:cleanrules on Maven Central.

Why three truth values instead of true and false?

Because real data has holes. With two values, a missing field must become false (silently wrong) or an exception (one bad row aborts a batch). With Kleene logic it becomes unknown, with a structured reason the explanation shows, and a rule fires only when its condition is true. This is the same null handling as SQL. When you prefer errors, strict mode raises them. More

Why not just write conditions as functions?

A function can be run but not inspected. A tree can be explained (“short by 2”), written to JSON and read in another language, audited statically, evaluated column-wise over Arrow, and compiled into a Rete network. Actions, on the other hand, are ordinary code of your language: only conditions are data.

Does cleanrules call a language model?

No, and it never will: neither the core nor any binding calls a model. Agents will call cleanrules, through an MCP server and adapters (planned, phase O). More

Is it safe to load rules from a file I did not write?

That is the design goal. Rules are data and are never executed as code; there is no eval. Regular expressions use Rust's regex syntax, which runs in linear time. Readers enforce limits on size (16 MiB), JSON nesting (1024) and node depth (256), and reject unknown and duplicate keys. Bindings will read only map keys and public data attributes, so a rule cannot reach into the process. The core has no unsafe code.

How can eight languages behave identically?

There is one engine. Bindings only convert data and call it. On top of that, the specification defines every observable behaviour, and the conformance vectors check it: each binding will run all of them twice, once through its JSON entry points and once converting the inputs into native data and using the idiomatic API.

Are there decision tables, a text syntax and YAML?

Yes, since phase D, in the core, so every language inherits them: JSON and YAML rule files, a text syntax with its own parser aligned with fuzzytool's rule_from_text (RULE vip IF customer.years > 5 THEN discount = 0.15), and decision tables with DMN hit policies, read from JSON, YAML or CSV or built from rows and data frames. Rules can name their actions, which each program resolves in a registry of its own.

How fast is it?

About 7.2 µs to evaluate 12 rules on one input, keeping every result tree, on an Apple M5; 6.4× and 6.7× faster than zen-engine 2.1.6 on one workload, while doing more work. Read the benchmarks page for the method and the caveats before quoting either figure.
