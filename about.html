About cleanrules

An explainable rules engine with one Rust core and the same semantics in every language, designed by its architect, Jose L. Salmeron. This page is about the author, the principles the project follows, and where the facts on this site come from.

The author

JLS

Jose L. Salmeron

Architect of cleanrules, who designed the library, its specification and its Rust core. Works on explainable artificial intelligence, fuzzy systems and decision support; also the author of fuzzytool.

Principles

What the project holds itself to.

Conditions are data

A condition is a tree that can be explained, serialized, audited and read in another language, never an opaque function. Actions are ordinary code of your language.

One engine

All semantics live in the Rust core. Bindings build rules idiomatically, convert data and translate errors; they never evaluate or explain on their own.

The specification is the oracle

A written specification and 2,508 conformance vectors define the behaviour. A change of semantics updates the specification, the vectors and the core together.

Determinism

The same inputs give the same decision, firing order and explanation in every language. Nothing depends on hash-map order or memory addresses.

Every result explains itself

Every engine returns a result with explain(); explanations are part of the public API, with a JSON form in the specification.

No eval, no surprises

Rules are never code: parsers have limits, regular expressions run in linear time, and the core has no unsafe code.

Family

A sibling of fuzzytool.

cleanrules shares its author and its style with fuzzytool, a fuzzy-logic toolkit for Python: the same operators (&, |, ~), name-resolved registries and the verbs explain(), audit(), summary() and rule_from_text(). fuzzytool's t-norms, s-norms and complements are the reference for the fuzzy logic planned in the core (phase J).

Sources

Where the facts on this site come from.

  • Python code and output on the manual and example pages was run with the Python binding built from the repository at commit 29b1ca3, on CPython 3.14.6 (free-threaded build). Cells on a page run in order in one session.
  • Rust code and output was compiled and run against crates/core at the same commit.
  • JSON documents were written by the core. For every worked example, the Python rules, the Rust rules and the JSON rule set were checked to be the same document, and Python's decision, explanation and summary documents equal the core's for the same input.
  • C programs were compiled against the C ABI (crates/ffi) built from the repository and run next to each example's JSON rule set.
  • TypeScript code and output was run with Node 26.13 on the JavaScript binding built from the repository at commit 01ea4a4 (its native addon, and its WebAssembly build, which printed the same), and type-checked with tsc. C++ programs were compiled as C++17 against cleanrules.hpp at the same commit, installed with CMake, and run. For every worked example, the TypeScript rule set writes the same document as the JSON tab, the C++ rules in the rule syntax read as that document, and both give the decision, explanation and summary the core gives.
  • Java code and output was run with the Java source launcher on OpenJDK 27 against the Java binding built from the repository at commit a1758c5 (bindings/jvm, which targets Java 25) and the C library built with cargo at the same commit; for every worked example, the Java rule set writes the same document as the JSON tab and gives the decision, explanation and summary the core gives.
  • Code in Scala, Go and Erlang is a design preview of bindings that are not there yet (the Scala 3 layer is being written); it may change and does not run.
  • Status and roadmap come from docs/PLAN.md and CHANGELOG.md; benchmark figures from benchmarks/results/.
