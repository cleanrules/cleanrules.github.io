Benchmarks

Numbers, with the method and the caveats.

The first measurements of the Rust core, taken on 2026-11-01 with criterion, and a comparison with zen-engine on the same rules. Every figure below is copied from the result files in benchmarks/results/.

Read these as a first data point, not a verdict. One workload, one machine, the Rust core only. They say nothing yet about other rule sets, other hardware, or the cost of crossing into Python, JavaScript or the JVM, which each binding will measure on its own. Compare runs on the same machine only.

Method

Criterion, release profile, confidence intervals.

The suites use criterion 0.8 (without its default features: no plots, no rayon). Each case reports criterion's estimate of the mean time per iteration and its 95 % confidence interval. Inputs are wrapped in black_box, and single-input cases cycle through the 1,000 applicants, so each iteration evaluates the next one.

Two suites live in crates/core/benches/:

  • eval: one input and batches of 1,000 under first, priority and collect; one condition tree; reading and writing the rule set as JSON.
  • explain: explaining 1,000 decisions, with and without writing each explanation as JSON text; evaluating and explaining together; the summary of the rule set.

Every evaluation keeps the full result tree of every rule, because that is what explain() needs and what a decision document records. Nothing in these numbers turns that off.

Workload

Twelve loan screening rules, 1,000 applicants.

Both suites and the comparison share one workload (crates/core/benches/common): a rule set that uses every family of node, and deterministic applicants from a fixed-seed linear congruential generator, so every run sees the same inputs. About one applicant in ten has no score, and one in twenty has a null income.

The rules, in order. Each outputs its name and rate = base_rate × n, where n is its position (1–12).

Applicants

  • age: an int from 16 to 85;
  • income: a float from 5,000 to 124,000, null for about 1 in 20;
  • debt: a decimal with two places, up to 89,999.99;
  • score: an int from 300 to 849, missing for about 1 in 10;
  • country: one of ES, FR, DE, US, KP, MX, IT;
  • employment: employed, self_employed, student or retired;
  • email: one of four addresses, one of them malformed;
  • base_rate: the decimal 1.25.

Missing scores and null incomes exercise unknown truth values and their reasons on every run, and the decimal debt exercises exact comparison and conversion to float for arithmetic.

What the numbers say

  • Evaluating one applicant against 12 rules, keeping all result trees, takes about 7.2 µs under first, 7.6 µs under priority and 8.8 µs under collect, where every fired rule is selected and its payload evaluated.
  • Building an explanation from a decision takes about 11.5 µs; evaluating and explaining together, about 19–21 µs per input.
  • Writing the explanation as JSON text costs about four times as much as building it (58 µs against 11.5 µs). The roadmap lists optimising it as a task of its own, to be justified by a benchmark.

What they do not say

  • The evaluate/batch_1000/priority interval is wide (9.47–11.16 ms): that case was noisy in this run, so its estimate is less precise than the others.
  • The suite's evaluate/batch_1000/first (7.97 ms) and the comparison's cleanrules case (7.22 ms) come from separate runs and loops (evaluate_many against a loop over evaluate); do not read the difference as a speed-up.
  • No parallelism is involved: everything runs on one thread.

Comparison

zen-engine 2.1.6 on the same rules.

zen-engine is a Rust decision engine for JDM decision tables. In benchmarks/zen the same 12 rules become one zen decision table, compiled and evaluated without trace, on the same 1,000 applicants. Time is for 1,000 evaluations.

first7.22 ms7.22 ms – 7.23 ms46.42 ms46.37 ms – 46.47 ms6.4×

Agreement is checked before measuring

For every one of the 1,000 applicants, under first and under collect, the benchmark asserts that both engines select the same rules, and that zen leaves its input unchanged. They agree on all of them; the check was verified to catch a deliberately altered row. The intervals do not overlap.

How each side is driven

  • cleanrules: a loop calling RuleSet::evaluate on each input.
  • zen: a loop calling Decision::evaluate on a clone of each prepared input, polled to completion with a no-op waker, since a decision table has no asynchronous node; no executor is measured. Inputs are converted to zen's JSON once, before timing, with decimals as floats.

The engines do not do the same work. cleanrules evaluates every rule and keeps every result tree, so that the decision can be explained and written as an audit record. zen's first hit stops at the first matching row and keeps no trace. The factor therefore compares cleanrules doing more work against zen doing less.

One workload, one machine. 6.4× under first and 6.7× under collect hold for this rule set on an Apple M5. Other rule sets, larger tables, zen features not used here, or other hardware may give different results. Nothing here measures the bindings.

Reproduce

Run them on your machine.

shell
git clone https://github.com/cleanrules/cleanrules
cd cleanrules

# The core's suites
cargo bench -p cleanrules --bench eval
cargo bench -p cleanrules --bench explain

# Save a baseline, then compare a later run with it
cargo bench -p cleanrules -- --save-baseline mine
cargo bench -p cleanrules -- --baseline mine

# The zen-engine comparison (a separate crate, not built in CI)
cargo bench --manifest-path benchmarks/zen/Cargo.toml

The comparison is a separate crate outside the workspace, so the core never depends on zen-engine. On macOS 27, Xcode's strip breaks one of zen's procedural macros in the release profile, so that crate disables strip for build dependencies.

The project's rule is that nobody claims a performance improvement without a benchmark: changes to hot paths are measured against the stored baseline before and after. Each binding will add its own measurements of data conversion overhead as it lands.
